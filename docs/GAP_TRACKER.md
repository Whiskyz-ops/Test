# Coverage Gap Tracker

Living document tracking everything WISING does **not** yet model, viewed through three separate lenses — **India-only** (a taxpayer living solely in India with only Indian income), **US-only** (solely US), and **cross-border** — so domestic accuracy is tracked with the same rigor as treaty work.

**Last verified against live sources: 11 July 2026.** Items marked "verified" were checked by web research on that date, not recalled from memory. Re-verify time-sensitive rows (rates, thresholds, treaty status) every quarter and after every Union Budget / US tax act.

**Status legend:** ✅ modeled · 🟡 partial · ❌ missing · 🔍 needs code verification · 🚫 out of scope by design

**Build Now? legend** (added per request — divides every row by whether *I* can build it without waiting on anything):
- 🟢 **Now** — every input already exists somewhere in Layer 1 (India or US); this is engine/UI work only, no form changes needed. Where only *part* of a row is buildable now, the Detail column says so explicitly.
- 🟡 **Needs field** — genuinely blocked until a new Layer 1 field is added (via an Antigravity prompt or direct edit) and round-tripped back.
- ⚪ **N/A** — doesn't fit the Now/Needs-field frame: already in flight with a prompt issued, a recorded out-of-scope decision, or needs a Layer 1 coverage check before it can even be classified.

**In-product surfacing:** every 🚫/assurance row that is not rule-encodable (GAAR, STT, payer-side TDS, clubbing depth, FICA levy, FATCA Ch.4, mocked uploads, plus the MLI/DTAA assurances) is ALSO shown inside the Monitor itself — the "Deliberately out of scope" card at the bottom of the overview, built by `buildScopeNotes()` in conflicts.js and gated per profile (e.g. the payer-TDS note only appears for business profiles, FICA only when US wages/SE income exist). The tracker records the decision; the Monitor discloses it to the professional.

**Priority legend:** P1 = real money exposure computable or misstatement risk now · P2 = valuable, needs new Layer 1 fields or moderate build · P3 = completeness/edge audience

## H. Prefilled-return / e-filing readiness — recorded 21 Jul 2026

The product direction is now explicit: prefilled, downloadable tax returns and forms (users have already entered the relevant facts on Layer 1) come before PD-1's branded advisory report matures further, with e-filing to follow. That changes the acceptable-error bar for anything that reaches `documents`/`taxComputation`/`returnForms`/`ftcReport`/`withholding` — those fields stop being an advisory finding with a "confirm with a preparer" recommendation attached, and start being literal content on a form a taxpayer might submit as-is. Everything in sections A-G above was scoped and prioritized against the *advisory* bar; this section re-examines the same engine against the *filing* bar, prompted directly by that product clarification rather than a code review.

**H.1 — Verified invariant: Monitor's pace-projected fields don't currently leak into filing output.** `monitoring.js` carries two families of "~"/"at current pace" projected dates — the residency day-counter's `crossDate`/`flipDate`/`dateLabel` (line ~79-90, an average-pace extrapolation from an aggregate day-count, not a real arrival-date reconstruction — see the Monitor's own residency-date discussion) and the limit gauges' `breachDate`/`dateLabel` (line ~226-228, same linear methodology applied to FBAR/8938/LRS/FEIE). Grepped `conflicts.js`'s six `buildXxx` functions that assemble `documents`/`taxComputation`/`returnForms`/`ftcReport`/`withholding`/`scopeNotes` (buildDocuments, buildFtcReport, buildTaxComputation, buildWithholdingSummary, buildScopeNotes, buildReturnFormDetermination) — none of them reference `monitoring.*`, `dateLabel`, `crossDate`, `flipDate`, or `breachDate` anywhere. The only monitoring field reaching `summary` is `monitoring.calendar.next.dateLabel`, which is the Compliance Calendar's own label — computed from real fixed statutory due dates (literal `d(year, month, day)` calls), not a pace projection; a different, reliable computation that happens to share a field name with the risky ones. **Rule to preserve, not just a one-time finding:** any future `monitoring.js` field carrying a projected/"~" value must never be read by those six `buildXxx` functions or by any prefill/PDF/e-file exporter built on top of them. If a real filing artifact ever needs an actual residency-start date (US dual-status returns have one), that requires Layer 1 to collect a real arrival date — not a better version of the pace formula, since no formula can produce information that was never entered.

**H.2 — What already exists to build on.** `computed.reconciliation`'s cross-basis rows already carry an `estimate: true` field (computation.js:1561, the US-business-income-approximated-at-Indian-net row) that the UI surfaces as a small amber "est." badge (`monitor-next/components/Views.jsx:800`). That's the right pattern — a machine-readable provenance flag the render layer turns into a visible caveat — just applied in exactly one place out of the roughly fifteen that would need it once the same data starts becoming form content instead of a dashboard number.

**H.3 — The actual list: self-documented simplifications that feed `documents`/`taxComputation`/`returnForms`/`ftcReport`/`withholding` today** (i.e., would land on a prefilled form as-is, not just inside a finding's advisory text). Every item below is quoted from the engine's own existing comments, not newly discovered — the gap is that none of them currently carry a machine-readable flag the way H.2's one example does.

*Completeness gaps — a required form/schedule/line could be silently absent, which is worse than an approximate number:*
- **CFC/GILTI (normalize.js:2698-2700):** `returnForm: "Foreign local return (not modeled) + Form 5471 (informational, US) + GILTI on Schedule 1"` — the foreign local return isn't identified at all for a taxpayer with a CFC, and the GILTI income figure itself is "a hand-entered estimate, since full GILTI/QBAI/tested-income computation from the CFC's own books isn't modeled yet." Prefilling for a CFC-holding taxpayer today would omit a required filing and present an unverified number as if it were computed.
- **Speculative-loss carry-forward (conflicts.js:985, 999):** "not modeled at all" in the loss set-off table that feeds Schedule CFL/BFLA — a real carry-forward bucket the schedule would simply omit for a taxpayer who has one.

*Numeric approximations feeding a real return-line amount:*
- **India surcharge marginal relief (computation.js:452, 740):** "simplified marginal relief" — feeds the actual India tax liability line.
- **DTAA NR-interest marginal rate (computation.js:603-606):** "a planning-grade approximation that doesn't account for loss-set-off ordering" — feeds the s.115A/s.159 income-tax computation.
- **US business income (computation.js:1561-1563):** "US net approximated at Indian net — diverges with US depreciation schedule" — feeds actual US Schedule C net income; already carries H.2's `estimate: true` flag in the reconciliation view, but that flag doesn't propagate into `taxComputation` itself.
- **India ss.424/425 interest (conflicts.js:415-417) + US Form 2210 penalty (conflicts.js:471-521):** both are literal return lines (ITR Part B-TTI's interest schedule; Form 2210 itself), not just advisory findings. s.425's narrow income-timing relief "isn't modeled... can overstate the estimate for late-year income"; Form 2210's Q4 rate is "approximated at Q3's rate — not separately verified."
- **§72(t) early-withdrawal penalty (conflicts.js:531-556):** assumes the full 10% whenever the age test fails, with zero statutory exceptions modeled (death, disability, SEPP, first-time-homebuyer, education, medical, birth/adoption) — a real Form 5329 line that could be materially wrong for anyone who genuinely qualifies for an exception.
- **FTC average-rate approximation (conflicts.js:921-932):** "the general FTC computation only approximates" the real graduated-rate mismatch — a real Form 1116 credit amount.
- **FX conversion basis (conflicts.js:1103):** stated plainly as "an approximation" — foundational, touches every cross-border dollar figure on both returns.
- **Schedule FA / Black Money Act asset values (conflicts.js:1363):** "approximated" — arguably the highest-stakes item on this list; Schedule FA is a heavily-scrutinized disclosure and Black Money Act misreporting carries severe penalty exposure, so an approximated value here is a materially different risk class than an approximated interest estimate.

**H.4 — Recommendation, two tracks, not one:**
1. **Before any of the above ships as prefilled content, extend H.2's `estimate`/provenance pattern to `documents`/`taxComputation`/`returnForms`/`ftcReport`/`withholding`, and have the download/PDF template (PD-1) render an explicit "Estimated — confirm before filing" marker on every such line** — not a plain number indistinguishable from a verified one. This is buildable immediately, independent of fixing any underlying simplification, and is the single highest-leverage thing to do before a prefilled form reaches a user.
2. **Prioritize closing gaps by real-world stakes, not code complexity.** Completeness gaps (CFC/foreign-return-not-modeled, speculative-loss-not-modeled) and high-penalty-exposure items (Schedule FA/Black Money Act, GILTI) should be closed or explicitly gated — "this profile has a fact pattern this platform doesn't yet support for prefill; consult a preparer" — before numeric refinements (interest-rate approximations, marginal-relief simplifications) that are directionally correct and merely imprecise.

**H.5 — Entity-agnostic audit — recorded 21 Jul 2026.** Prompted by a user report that "income exposed" showed $0 for the `us_ccorp_indian_sub` profile despite real business income on file. The single-field fix (Monitor's `incomeExposedUsd`) was correct but symptomatic of a much larger pattern: this whole product was built and verified almost entirely against individual/HUF taxpayers, and a US or India *entity* taxpayer silently breaks several genuinely computational paths, not just display fields — directly relevant to H.1-H.4 above, since a wrong FTC relief figure or a "$NaN" tax-computation trace is exactly the kind of thing H.4's "Estimated — confirm before filing" marker can't paper over (it isn't an estimate, it's a bug).

*Root cause.* `model.income.us.total`/`usSourceTotal`/`foreignSourceTotal` (engine) and the DAG's mirror aggregate are INDIVIDUAL-1040-shaped (wages + interest + dividends + business_us + …), always `$0` for a business entity — an entity's real income is Schedule M-1 book-to-tax reconciled (`entity.usScheduleM1TaxableIncomeUsd` → `computed.usTax.totalIncomeUsd`), a completely separate data path Layer 1 never folds into the generic aggregate. Six distinct places read that always-$0 aggregate without checking entity routing first, corrupting real numbers (not just labels): India's own s.90 FTC relief for US tax paid, the FY↔CY Apportionment card, the income summary/headline total, the US Tax Computation trace (a literal "$NaN" in user-facing formula text — and its exact India-side analog, "₹NaN", on the entity tax-computation trace), the `underpayment_2210` finding (cites Form 2210/§6654, an individual-only statute, on a corporation), and CL-2's calendar-amounts feature (same wrong statute). India's own income aggregate was NOT affected — India's business-entry pipeline is shared between individual and company/firm taxpayers, so entity PGBP income already flowed through correctly there.

*Decision on how to fix it.* The engine (`engine/*.js`) is frozen per the DAG-migration policy (`docs/DAG_MIGRATION_TRACKER.md`) and these are engine-rooted bugs. Since engine and DAG are now numerically identical (SYS-3 closed, byte-for-byte parity fully proven across ~10,000 fuzzed profiles), the byte-identical invariant no longer needs to be maintained as a goal in itself — explicit product direction (21 Jul 2026): **fix every one of these bugs correctly in the DAG only, never touch `engine/*.js`, and update the fuzzer/shadow-mode/test-adapter tooling to allow this specific, catalogued set of known, intentional divergences.** The DAG is now the more-correct implementation for a US-entity, India-entity, or NRA taxpayer on exactly the paths below; everywhere else, and for every individual/HUF taxpayer, byte-identical parity is still required and still enforced.

*What was fixed, and where (all in `prototypes/graph-pilot/*-nodes.js`, synced to `monitor-next/lib/dag/`):*
- `ustax-full-nodes.js`'s `usEntityResult()` (the C-Corp/S-Corp/partnership/trust tax result): `foreignSourceIncomeUsd`/`usSourceIncomeUsd` now derived from the entity's own taxable amount instead of the individual aggregate.
- `ustax-full-nodes.js`'s `apportionmentResult` override: `usCyTotalUsd` uses the entity-aware figure **only when `usTaxResult.isEntity`** — an early, broader version of this fix swapped it in unconditionally and introduced a real new divergence for FEIE-electing individuals and NRAs (both legitimately narrower than the raw aggregate for unrelated, correct reasons); caught by `run-fuzz.js` and narrowed back to entity-only.
- `xborder-full-nodes.js`'s `usSourceTotalUsdBoundaryFtc`: now reads the routed `usTaxResult.usSourceIncomeUsd`. Fixed India's own s.90 FTC relief for a US entity, and incidentally fixed a latent NRA-side inconsistency in the same boundary (confirmed a genuine additional correctness improvement, not a regression).
- `agg10-nodes.js`'s `headlineResult`: `totalIncomeUsd` now sums the entity's own taxable income when `usTaxResult.isEntity`, instead of silently dropping it.
- `agg10-nodes.js`'s `us1ShouldFire` override: `underpayment_2210` (Form 2210/§6654) suppressed for a US entity — a corporation's estimated-tax underpayment is Form 2220/§6655, a distinct, unmodeled regime; showing nothing is more correct than showing the wrong form's number.
- `calendar-amounts-nodes.js`: `calendarAmountsResult.us.installments` is `[]` for a US entity, same reasoning, mirroring the pre-existing `!inAdvTaxObliged` gate already used on the India side.
- `report-batch2-nodes.js`'s `buildTaxComputationUsResult`: a genuine entity branch (Taxable income → flat/pass-through tax → Total) replaces the individual row set the engine reuses verbatim for an entity, which is where its "$NaN" comes from (`ordinaryTaxableUsd`, `saltCapUsd`, etc. are all `undefined` on the entity result object).
- `report-batch3-nodes.js`'s `buildTaxComputationIndiaResult`: same fix, India side — a genuine entity branch (Taxable income → tax at entity/MAT rate → surcharge → cess → total), fixing the exact "₹NaN" analog (`i.totalNormalInr` interpolated unconditionally into a slab-rate formula string that only individual returns populate).

*Tooling updated to allow the (now-deliberate, catalogued) divergences instead of failing on them:* `prototypes/graph-pilot/run-fuzz.js` (new "Section D" allowlist — `KNOWN_US_ENTITY_DIVERGENT_PATHS`/`KNOWN_INDIA_ENTITY_DIVERGENT_PATHS`/`KNOWN_NRA_DIVERGENT_PATHS`, plus a named exception in `compareFindings` for `underpayment_2210`), `run-agg10.js`, `run-report3.js`, `run-analyze.js`, `run-ustax-full.js`, `run-calendaramounts.js` (each gated strictly on the profile's actual taxpayer shape, never on label), and `monitor-next/test-adapter.mjs` / `monitor-next/lib/shadow-core.js` (same allowlist convention, so shadow mode in the running app doesn't flag these as live discrepancies). Every allowlist entry is scoped to the specific field paths actually affected — verified via `run-fuzz.js` at 5,000+ randomly generated profiles per seed with **zero** unexplained divergences remaining, and the full `run-*.js` harness suite (40+ files) green.

*Known remaining gap, not fixed here (out of scope — a data-modeling gap, not a wiring bug):* the Reconciliation view's "US income — by head" card still reads the individual-shaped aggregate directly and shows "No US income on file" for a US entity, inconsistent with the real $4.26M figure the Tax Computation card right below it now correctly shows. Modeling a real by-head breakdown of an entity's Schedule M-1 income is a genuine new feature (Layer 1 US Business currently collects only the aggregate), not a bug fix — flagged here rather than silently left inconsistent.

## H.6 — Business entity coverage, Phase 1: silently-wrong entity routing — recorded 21 Jul 2026

Follow-on to H.5. User direction: "we have made everything possible from the POV of an individual but we haven't even touched the business part yet... there are so many entity types apart from individual." A scan of both sides' entity-type enums found two MORE cases where a real, selectable Layer 1 entity type was silently taxed as a plain individual — not a display bug like H.5's "$NaN", but the entity paying the wrong tax entirely, with no error or flag. Phase 1 (of a 3-phase plan: this routing fix, then US state income tax, then a real multi-entity/entity-graph model) closes these two. Both fixes are DAG-only (`prototypes/graph-pilot`, synced to `monitor-next/lib/dag`), per the same standing "engine frozen, fix the DAG" policy H.5 established — `engine/*.js` untouched.

**H.6.1 — India: AOP/BOI and Trust/NGO/Political Party taxed as a plain individual.** Layer 1 India's `entity_type` dropdown has 8 real values: `individual, huf, firm, llp, company, aop, trust, ajp, local`. `normalize.js`'s routing (`if (E.indiaIsCompany || E.indiaIsFirm)`) only recognizes `company` and `firm/llp/local` — `aop` and `trust` fall through to the individual/HUF slab computation (standard deduction, §156/§87A rebate, the works). That's correct for `huf` and defensible for `ajp` (both genuinely use individual-style slab rates under Indian law), but wrong for the other two:
- **AOP/BOI (s.167B):** taxed at the Maximum Marginal Rate (42.744% = 30% top slab × 1.37 old-regime top surcharge × 1.04 cess) whenever member shares are indeterminate — or determinate but any member's own income exceeds the basic exemption, the common case for a real commercial AOP. Layer 1 collects no member-share-determinacy facts at all, so MMR (the statutory default for the unestablished case, not a guess) now applies unconditionally. Fixed in `entitytax-nodes.js`.
- **Trust/NGO/Political Party:** the engine's OWN `computeIndiaItrForm` (computation.js:1753-1756, ported unchanged in `itrform-nodes.js`) already recommends ITR-7 "claiming tax exemptions under Trust & NGO Tax Exemptions" for this exact `entity_type` value — i.e. the engine's own form-determination logic already assumes s.11/12A (charitable) or s.13A (political party) exemption, while `computeIndiaEntityTax` computed a nonzero individual-slab tax on the same income, directly contradicting its own ITR-7 recommendation. Aligned in the DAG: treated as exemption-claiming (tax = 0), with the compliance conditions (85% application-of-income test, valid 12A/12AB registration, s.13A's books/audit/cash-donation conditions) named as unverified rather than silently assumed met. A genuine private/family trust (not claiming any exemption) is a different real-world case this Layer 1 field cannot currently distinguish from the charitable/political case — not solved here, recorded as a further known gap.

Both routing fixes cascade into `isEntityTaxpayer`, `model.entity.isBusiness`/`indiaReturnForm` (AOP → ITR-5, Trust → ITR-7), the `model.assets.businessEntities[]` return-form trace, and — for AOP specifically, since its tax AMOUNT is now genuinely different, not just its trace — nearly everything India-tax-derived: FTC both directions, headline/summary totals, several finding IDs (`ftc_gap`/`promoter_buyback_additional_tax`/`carry_forward_losses_not_applied` all correctly disappear for an exempt trust), monitoring health. Every touched site (8 files: `entitytax-nodes.js`, `india-full-nodes.js`, `india-tax-combined-nodes.js`, `agg10-nodes.js`, `assets-nodes.js`, `checks-registry-nodes.js`, `findings-batch3-nodes.js`, `report-batch1-nodes.js`) was individually reviewed, not blanket-widened — e.g. the company-specific POEM-mismatch finding correctly stayed company-only, since AOP/Trust have no incorporation-place residency test in the same sense.

**H.6.2 — US: a trust (Form 1041) always computed $0 entity-level tax, even when it should owe real (and highly compressed) bracket tax.** `computeUsEntityTax` treated a trust identically to an S-corp/partnership: 100% pass-through, $0 at the entity level. Investigation found this was actually *defensible* for a fully-distributing trust (a real "simple trust" under §651 genuinely owes ~$0 at the entity level — the distribution deduction offsets DNI) — but Layer 1 US had no field at all for the case that should NOT be $0: a trust that retains (accumulates) income. Its only trust-income field is framed as "Beneficiaries' Share of Income," implying full distribution, and `corporate_financials.schedule_m1` is explicitly gated to `ccorp/scorp/partnership` only — never populated for `trust`.

Closed with one new Layer 1 US field, not a caveat-only fix (user's explicit choice over a smaller, no-new-field option): **"Income retained by the trust (not allocated to any beneficiary this year)"**, added to the trust profile step (`layer1_us.html`, `usState.profile.trust_retained_income_usd`, defaults to 0). Wired through `ustax-full-nodes.js`'s `usEntityTaxResult`:
- Distributed portion (the existing "beneficiaries' share" aggregate) stays untaxed at the entity level — taxed on the beneficiaries' own returns instead, same as before.
- Retained portion is taxed at the real §1(e) trust/estate brackets — far more compressed than the individual brackets (37% starts around $15,650 vs. $640,600+ for a single individual). TY2025 figures (Rev. Proc. 2024-40) are the best-available confirmed numbers at hand; TY2026's exact Rev. Proc. 2025-32 trust/estate table hasn't been independently re-verified, flagged as such in-code rather than asserted as final.
- `totalIncomeUsd`/`usSourceIncomeUsd` report the FULL economic total (distributed + retained) for cross-border FTC/apportionment purposes, which want "how much did this entity earn," not "how much is taxed at its level" — only `taxableIncomeUsd` narrows to the retained slice.
- `report-batch2-nodes.js`'s Tax Computation trace gained a genuine trust-specific row set (total → distributed (not taxed here) → retained → bracket tax → total), replacing the flat-rate/pass-through shape that doesn't fit a bracket computation.

Verified: hand-computed bracket math on a $25,000-retained synthetic case matches the DAG exactly ($7,236.50); browser-confirmed live (both the new Layer 1 US field — visibility toggle, value persistence — and the Reconciliation view's resulting trace).

**H.6.3 — Verification.** `run-fuzz.js`'s existing entity-type mutation pool already generates `aop`/`trust`/`coop` (India) and `trust` (US tax_entity_type) — extended its Section D allowlist with `KNOWN_INDIA_AOP_TRUST_DIVERGENT_PATHS` and `KNOWN_US_TRUST_DIVERGENT_PATHS` (each gated strictly on the profile's actual `model.entity` shape) plus new `DAG_ONLY_KEYS` entries for the fields with no engine equivalent at all (`indiaIsAop`/`indiaIsTrust`/`trustDistributedUsd`/`trustRetainedUsd`/`trustBracketBreakdown`) — mirrored into `shadow-core.js` and `test-adapter.mjs`. Clean across 4 fuzz seeds / 13,000+ generated profiles with zero unexplained divergences, full `run-*.js` harness suite (40+ files) green, `test-adapter.mjs`/`test-shadow.mjs` green (neither exercises AOP/trust today since none of the 11 real demo profiles use those entity types — coverage here is from the fuzzer and direct synthetic tests, not the fixed-fixture harnesses). `coop` (India `entity_type`) appears in the fuzzer's mutation pool but is NOT a real, reachable Layer 1 dropdown value — noted so it isn't mistaken for a live gap.

**Not done in Phase 1 (Phases 2-3, separate work):** US state income tax (still $0 everywhere, blocks real multi-state entity apportionment) and a genuine multi-entity/entity-graph model (today the product analyzes one taxpayer at a time; an individual who owns an entity AND has personal K-1 income elsewhere has no connected representation).

## H.7 — Business entity coverage, Phase 2: US state income tax — recorded 21 Jul 2026

Follow-on to H.6. `computeUsStateTax` (`computation.js:1133-1182`) — the engine's only state-tax computation — had two real gaps, one on the individual side and one on the entity side, both closed here, DAG-only, `engine/*.js` untouched:

**H.7.1 — Individual: only CA/NY modeled; every other state, including the two genuinely tax-free ones and the top "NRI top-5" states, silently returned nothing.** A prior GAP_TRACKER pass ("US-12") had this row down as "$0 everywhere," which was stale — `computeUsStateTax` already modeled CA and NY correctly. The real gap was narrower but still real: `US_STATES` (constants.js) has exactly two entries, so a taxpayer domiciled in any other state got a silent `null` — indistinguishable, from the UI, between "genuinely zero" and "not computed." Two concrete cases closed in `findings-batch5-nodes.js`'s `usStateTaxResult`:
- **New Jersey**: a real bracket table added (`US_STATES_NJ_NY_SHAPE_EXT`), same shape as CA/NY (`BRACKETS`/`STD_DEDUCTION`/`DEPENDENT_EXEMPTION_USD`) so `report-batch2-nodes.js`'s existing trace renderer needed no structural changes — only its hardcoded CA/NY label text genericized via new `standardDeductionLabel`/`dependentExemptionLabel` fields (NY's own exact original wording — "Less NY dependent exemption ($1,000/dependent)" — preserved byte-for-byte via an explicit `state === "NY"` branch, so this genericization introduces zero avoidable divergence from the engine on the one state the engine already covers). TY2025 NJ Div. of Taxation brackets (unchanged for several years) — best-available figures, not independently re-verified for the exact TY2026 vintage.
- **AK/FL/NV/SD/TN/TX/WA/WY** (`NO_INDIVIDUAL_INCOME_TAX_STATES`): states with genuinely no individual income tax. Previously indistinguishable from "not computed" — both silently returned `null`. Now returns an explicit `{ noIncomeTax: true, totalTaxUsd: 0, basis: "<State> has no individual income tax." }` result instead of nothing, surfaced in `report-batch2-nodes.js`'s trace as a short confirmation card rather than the full bracket-walk shape, and in `checks-registry-nodes.js`'s `state_income_tax` pass-check text (distinguishing "no income tax at all" from "nets to zero at this state's own rates").

Every other individual-side US state remains genuinely unmodeled — not claimed otherwise.

**H.7.2 — Entity: `computeUsStateTax` excludes ALL business entities unconditionally** (`computation.js:1129-1132`'s own comment: business entities "file separate state franchise/entity-level returns, an unrelated and unmodeled regime, so this function only fires for individual filers"), meaning a US C-Corp, S-Corp, partnership, or trust got the exact same silent `null` regardless of state — no distinction between "this state has real, unmodeled entity-level exposure" and "this entity genuinely owes nothing." Closed with a new `usEntityStateTaxResult` node (`ustax-full-nodes.js`, reusing the pre-existing shared `usState.profile.state_of_domicile` Layer 1 field — already collected for entities via the `corp-domicile` select, so no new Layer 1 field was needed here unlike H.6.2's trust field) at the same "planning-grade, single-state, no apportionment" fidelity as the individual brackets, with everything else honestly flagged unmodeled rather than defaulted to zero:
- **C-Corp in CA/NY/NJ**: a real, if simplified, entity-level income tax — flat top-bracket rate (CA 8.84% is genuinely flat; NY's 7.25% and NJ's 9% are each real top brackets with the lower-bracket/minimum-tax/surtax detail explicitly excluded and named in the finding text), computed on the entity's own federal taxable income (`usEntityTaxResult.taxableIncomeUsd`).
- **S-Corp/Partnership (any state)**: pass-through at the state level too, same as federal — no entity-level computation, but flagged that a state PTET (pass-through entity tax) election isn't checked.
- **Trust (any state)**: state fiduciary income tax has its own throwback/accumulation-distribution rules, materially different from the federal §1(e) brackets in H.6.2 — not modeled, flagged as such.
- **TX/WA (any entity kind)**: deliberately NOT given the individual side's "$0, confirmed no tax" treatment — Texas's Franchise (Margin) Tax and Washington's B&O tax are real, gross-receipts/margin-based taxes with no income-tax analog to reuse the bracket model for. The finding names the actual regime and explicitly says not to assume $0.
- **Every other state**: genuinely not modeled, same honest "don't assume $0" framing.

Surfaced as two new finding IDs only (`us_entity_state_tax` when a real amount is computed, `us_entity_state_tax_not_modeled` for every caveated case) — not a new `taxComputation`/document card, to avoid a frontend schema change for a first cut; the Monitor already renders findings generically.
